# 1,000개 노드 성능 측정

`npm run test:perf`로 보드와 분석 기록 규모를 함께 잰다. 브라우저 경로는 `CT_CHROME` 으로 넘긴다.
언어 서버를 1,000번 부르는 대신 저장 파일(`.code-trail/trails/<id>.json`)을 직접 만들어
넣는다 — 여기서 재려는 것은 심볼 해석이 아니라 **불러오기와 그리기**다.

노드는 폭 우선(한 부모당 자식 4개)으로 만든다. 깊이만 늘리면 실제 트레일과 모양이 달라
연결선 수와 열 수가 현실과 어긋난다.

## 측정값

Windows 11 / Node 22.17.1 / Google Chrome 152.0.7977.76 / 뷰포트 1600×1000 / 노드 1,000개.

| 항목 | 시간 | 비고 |
| --- | --- | --- |
| `flattenTree` | 0.6ms | 모델을 깊이 우선으로 펴기 |
| `autoPlace` (좌표 없음) | 8.2ms | 1,000개 전부 자동 배치 |
| `autoPlace` (좌표 있음) | 0.2ms | 저장된 자리를 그대로 쓸 때 |
| `connectors` | 0.5ms | 곡선 999개의 `d` 만들기 |
| `startServer` | 51.5ms | 저장된 트레일을 읽어 들이는 것까지 |
| 트레일 탭 첫 화면 | 881.7ms | 구현서 19의 목표(1초) 안 |
| 보드 전환 | 714.2ms | 재렌더 + 크기 측정 + 연결선 |
| 스크롤 20회 | 6.2ms | |

1.7.0 에서 노드마다 하는 일이 늘었다 — 헤더에 검토 표시와 노드 메뉴 버튼이 붙고,
접힌 노드는 하위 요약을 그리고, 코드 화면은 여백 표식 색인을 만든다. 첫 화면이
831.1ms → 881.7ms 로 약 6% 늘었고 목표(1초) 안이다. 요약과 여백 색인은 트리를 **한 번**
훑는 순수 함수(`subtreeSummary`·`buildGutterIndex`)라 노드 수에 선형이다.

## 병목

**배치 계산은 병목이 아니다.** 넷을 합쳐도 7ms 아래고, 저장된 좌표가 있으면 1ms 아래다.
`autoPlace` 의 겹침 회피(`placeNear`)가 유일한 이차 비용인데, 자리를 한 번 저장하고
나면 다시 돌지 않는다 — 자동 배치는 노드가 처음 생길 때만 필요하다.

**시간은 노드 본문을 그리는 데 들어간다.** 881.7ms 중 대부분이 노드마다 도는
토크나이저(`tokenizeLines`)와 그 결과를 span 으로 펴는 DOM 생성이다. 노드 하나가
평균 4줄짜리 본문인데도 이 정도이므로, 본문이 긴 실제 트레일에서는 더 든다.

보드 전환이 첫 화면과 비슷하게 드는 이유는 트리를 통째로 다시 그리고, 그 뒤
`useLayoutEffect` 가 1,000개 `.node` 의 `offsetWidth`/`offsetHeight` 를 읽으면서
강제 레이아웃이 한 번 더 일어나기 때문이다. 이 측정 자체는 한 번뿐이고 값이
안정되면 다시 돌지 않는다.

## 아직 손대지 않은 것과 그 이유

구현서 19는 "일반 리스트 가상화를 바로 적용하지 말고 1,000개 노드 성능 측정 뒤
병목 구간에만 적용한다" 고 했다. 재 보니 목표치(1초) 안에 들어오므로 **지금은
가상화를 넣지 않는다.** 연결선과 보드 좌표가 있는 화면에 가상화를 넣으면 화면 밖
노드의 크기를 모르게 되어 자동 배치와 연결선이 함께 망가진다. 얻는 것보다 잃는
것이 크다.

다음에 손댈 곳이 생긴다면 순서는 이렇다.

1. **코드 본문 지연 렌더링** — 접힌 노드의 본문은 토크나이저를 돌리지 않도록
   1.1.0에서 적용했다. 부모-자식 관계나 좌표를 건드리지 않는 범위의 개선이다.
2. **토크나이저 결과 캐시** — 같은 심볼이 여러 번 나오면 다시 자르지 않는다.
3. 그래도 모자라면 그때 가상화를 본다. 이때도 **크기는 미리 저장해 둔 값**을 쓰고
   화면 밖 노드를 지우지 않는 방식이어야 한다.

개별 기록은 64KiB로 제한한다. 화면은 필터 결과만 렌더링하지만 10,000개를 한꺼번에
표시하는 경우에는 브라우저별 재측정 뒤 목록 가상화를 검토한다.
